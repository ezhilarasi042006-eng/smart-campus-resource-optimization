# Cloud-Based AI-Powered Smart Campus Resource Optimization and Management System

CampusIQ is a responsive, cloud-ready academic prototype for managing campus spaces and shared equipment. It combines a Node.js/Express REST API, JSON-file storage, a responsive HTML/CSS/JavaScript interface, Chart.js visualizations, booking conflict checks, and explainable rule-based recommendations.

> **Prototype note:** “AI insights” in this version are generated by transparent rules, not a trained machine-learning model. Utilization percentages are illustrative sample values, not live sensor readings. Validate data and policies before any real-world deployment.

## Features

- Dashboard metrics for resource count, average utilization, active bookings, and resources needing optimization.
- Resource directory with search, category filters, capacity, location, utilization bars, features, and detail view.
- Booking workflow with name, email, resource, start/end date and time, and purpose.
- Server-side validation for required fields, email format, date order, past start times, unknown resources, and overlapping confirmed bookings.
- Booking IDs generated by the server; booking cancellation changes status and releases the time slot.
- Booking history with status filters and cancellation action.
- Chart.js utilization chart and analytics breakdown.
- Explainable recommendations: high demand at 80% or above, underutilized below 40%, and balancing suggestions.
- JSON persistence in `data/resources.json` and `data/bookings.json`.
- Responsive layout for desktop, tablet, and mobile.
- Health endpoint, API error handling, no database installation or API key required.

## Requirements

- Windows 10/11 (or macOS/Linux)
- Node.js 18 or later and npm
- A modern browser
- Internet access is only needed to load Google Fonts and Chart.js from their CDNs. The application API and JSON storage run locally. If offline, the interface still loads; the charts require the Chart.js library to be available.

## Windows installation and run

1. Download and extract the project ZIP.
2. Open the extracted folder named `Cloud-Based-AI-Powered-Smart-Campus-Resource-Optimization-and-Management-System`.
3. In File Explorer, click the address bar, type `cmd`, and press Enter. This opens Command Prompt in the project folder.
4. Confirm that `package.json` is present:
   ```cmd
   dir
   ```
5. Install the project dependency:
   ```cmd
   npm install
   ```
6. Start the server:
   ```cmd
   npm start
   ```
7. Open **http://localhost:3000** in your browser.
8. To stop the server, return to Command Prompt and press **Ctrl+C**.

The server should print a message similar to:
```text

```

## Main API endpoints

| Method | Endpoint | Description |
|---|---|---|
| GET | `/api/health` | Service health and timestamp |
| GET | `/api/resources` | List resources; optional `?search=lab` and `?category=Laboratory` |
| GET | `/api/bookings` | List reservations; optional `?status=Confirmed` or `?status=Cancelled` |
| GET | `/api/insights` | Utilization summary and recommendations |
| POST | `/api/bookings` | Validate and create a reservation |
| PATCH | `/api/bookings/:id/cancel` | Cancel a reservation by ID |

### Create-booking request example

```json
{
  "resourceId": "RES-005",
  "bookerName": "Priya Sharma",
  "email": "priya.sharma@example.edu",
  "start": "2026-12-01T10:00",
  "end": "2026-12-01T11:00",
  "purpose": "Capstone project discussion"
}
```

Send this JSON to `POST /api/bookings` with `Content-Type: application/json`. A successful response has HTTP status `201`; invalid input returns `400`, an unknown resource returns `404`, and a booking conflict returns `409`.

> Use a future date/time when testing. The server rejects bookings that start in the past.

```text
Browser (HTML + CSS + JavaScript + Chart.js)
                |
           fetch() / REST
                |
      Node.js + Express (server.js)
          /                 \
  resources.json         bookings.json
```

- `public/index.html` — dashboard layout, navigation, views, tables, and modals.
- `public/style.css` — responsive design system and component styling.
- `public/app.js` — API communication, rendering, filters, charts, forms, and notifications.
- `server.js` — REST API, validation, conflict detection, analytics rules, and JSON persistence.
- `data/resources.json` — sample campus resources.
- `data/bookings.json` — sample reservations.
- `package.json` — dependency and run scripts.
- `.gitignore` — excludes installed dependencies, secrets, logs, and editor files.

## Booking conflict logic

Two confirmed reservations conflict when they refer to the same resource and their time ranges overlap. The API checks:

`requestedStart < existingEnd AND requestedEnd > existingStart`

A cancelled reservation is excluded from conflict checks. This is appropriate for a single-process academic demo; a multi-instance cloud deployment should move reservations to a database with transactional/atomic conflict protection.

## Explainable optimization rules

- **High demand:** utilization is `>= 80%`; recommend alternative spaces or time slots.
- **Underutilized:** utilization is `< 40%`; recommend promoting the space for suitable activities.
- **Allocation balancing:** if both categories exist, suggest evaluating flexible activities for a potential shift.
- **Average utilization:** arithmetic mean of the sample utilization values across resources.

These rules are intentionally transparent. They do not predict future demand and do not constitute a trained ML model.

## Data and reset

The app writes reservations to `data/bookings.json`. Back up this file before editing or resetting it. The initial sample data is restored by replacing `data/bookings.json` with the original copy from a fresh ZIP extraction. Avoid editing the JSON while the server is running.

## Cloud deployment readiness and next steps

The project serves static assets and API routes from one Express process and reads the port from `process.env.PORT`. For a real cloud deployment:

1. Replace JSON storage with a managed database such as MongoDB Atlas or PostgreSQL.
2. Use transactions or unique/locking strategies to prevent concurrent booking conflicts.
3. Add authentication, role-based authorization, CSRF/rate limiting as appropriate, audit logs, and input validation.
4. Store configuration and credentials in environment variables; never commit secrets.
5. Use HTTPS, backups, monitoring, and centralized logs.
6. Deploy the Node app to a platform such as Render, Railway, Azure App Service, or AWS; configure a persistent database and health check at `/api/health`.
7. Replace illustrative utilization values with measured booking hours or sensor/occupancy data.
8. Later, add a trained forecasting model behind a separate analytics service after collecting representative, permissioned data.

## Testing checklist

The project has a built-in `npm run check` script for syntax validation. Use the following manual/API checks after installation:

- [ ] Server starts and dashboard opens.
- [ ] Health endpoint returns `status: "ok"`.
- [ ] Sample resources render and search/category filters work.
- [ ] Resource detail modal opens and its booking button preselects the resource.
- [ ] A valid future booking is saved and appears in the bookings table.
- [ ] An overlapping booking for the same resource returns HTTP `409`.
- [ ] An overlapping booking for a different resource is accepted if its dates are valid.
- [ ] Invalid email, missing fields, past start time, and end-before-start are rejected.
- [ ] Cancelling a booking changes status to `Cancelled`.
- [ ] A cancelled booking no longer blocks the same time slot.
- [ ] Analytics and recommendation pages render.
- [ ] Reloading the page preserves bookings stored in JSON.

## Limitations

- JSON file writes are intended for a single local Node process and small academic demonstrations, not concurrent multi-instance production hosting.
- Authentication and authorization are not implemented; do not expose this prototype publicly with real campus data.
- Utilization data is illustrative and must be replaced with verified operational data.
- Chart.js and Google Fonts are loaded from CDNs and need internet access unless locally bundled.
